# 상장 직전 전향적 검증 운영

## 2026-09-22 청약 일정 후보 원장

DART 달력과 실제 신고서 요약을 대조해 사진 20개 공모의 시작/종료일을 모두 확인했다. ipo_predictor/data/processed/upcoming_schedule_registry/20260922.json은 일정 검증 20건, 모델 승인 0건인 별도 원장이다. 확정 공모가·상장일·IPO 세부 분류를 추정하지 않는다. 등록된 자동 실행이나 실제 예측이 생긴 것은 아니다.

해당 원문은 이미 수집돼 재수집 없이 검증했다. 후속으로 정정·철회와 공식 상장일·종목코드를 확인하고, 예측 시점 이전에 검증된 피처가 확보된 경우만 모델 승인 경로에 연결해야 한다. 전체 기간 학습 수집을 반복하거나 소진된 2026년 평가 표본을 재튜닝하지 않는다. 상세 근거는 docs/예정기업_DART_공시계보_검증.md를 따른다.

## 2026-09-22 원천 보완과 청약/상장 분리

사진 속 20종목은 DART 공개 청약 달력에서 대응 일정을 확인했다. 현재 예정 기업 발견은 KIND 단독 결과를 전체로 취급하지 않고 DART 달력 후보와 함께 감사한다. 18개 이름 직접 일치, 스팩 2개 공식 법인명 대응 후보다. 상세 종목별 접수번호는 docs/청약예정_20종목_공식대조.md를 참조한다.

upcoming_ipo_collector는 이제 청약 일정·상태와 상장 일정·상태를 분리 저장한다. 상장일 미정인 청약 예정 기업을 서비스 후보에서 빼지 않는다. 서비스 후보와 모델 승인 여부는 다르다. 새 DART 달력 감사 CLI는 공개 원문을 실제 조회하므로 키가 필요하지 않지만 증권신고서 본문·정정 계보 검증을 대체하지 않는다.

```bash
python ipo_predictor/scripts/audit_dart_subscription_calendar.py \
  --year 2026 --months 9 10 11 \
  --output ipo_predictor/data/raw/dart_calendar_audit
```

이는 일정 감사 명령이다. 정기 실행을 등록한 것은 아니며 실제 앱 목록/모델 원장 자동 승격은 아직 차단돼 있다. 전체 테스트 159개 통과, 기존 경고 3개.

## 2026-09-22 연결 현황

- 공식 예정 후보 수집기를 추가했다. 기존 신규상장기업현황은 오늘까지의 상장 완료 이벤트용이고, 예정 후보는 KIND 공모기업현황을 별도로 조회한다. 공식 화면에서 조회 method/forward와 상세 연결의 bzProcsNo를 확인했다. 이 번호는 DART 접수번호라고 가정하지 않는다.
- 공식 안내: https://kind.krx.co.kr/listinvstg/pubofrprogcom.do?method=searchPubofrProgComMain . 이 화면은 상장주선인 제공 자료이며 오류·지연 가능성이 있다고 안내한다. 일정 후보 발견 자체를 최종 상장 일정 검증으로 승격하지 않는다.
- 목록과 다운로드를 9개 표시 필드 전체로 대조해 고유 업무번호를 연결한다. 회사명 단독으로 연결하지 않는다. 다운로드 헤더 변경, 100건 초과 페이지 미수집, 시장 불일치, 양쪽 값 변경은 실패 처리한다. 호출 사이 정정이 생겨도 조용히 합치지 않는다.
- 실제 검증 범위는 신고서 제출일 2026-06-01~2026-09-22, KOSPI/KOSDAQ 두 시장이다. 18건 수집, 그중 수집일 이후 상장 예정 5건. 전체 예정 IPO 모집단을 모두 확보했다는 뜻은 아니다. 과거 제출 후 장기 연기된 기업은 이 조회 창 밖일 수 있다.
- 첫 실호출에서 다운로드의 UTF-8 강제 디코딩 실패를 확인해, 원본 바이트를 보존하고 HTML 파서의 인코딩 판별을 사용하도록 수정했다. 재실행 성공 산출물: data/raw/upcoming_snapshots/20260922T162100211637. 원문 4개와 SHA-256·요청별 상태·시각 매니페스트를 저장했다. 실패 실행 기록도 보존했다.
- 후보 5건은 와이즈플래닛컴퍼니(9/23), 빅웨이브로보틱스(9/29), 글로벌테크놀로지(9/29), 덕산넵코어스(9/30), 브릴스(10/1)다. 이는 당시 공식 화면의 예정일이며 확정 거래 개시 보장이 아니다. 전부 model_eligible=false다.
- 신규 후보와 DART 고유번호·확정 종목코드·정정 계보·기관 피처를 연결하는 승인 어댑터는 아직 미완료다. 현재 환경 DART/KRX 키는 모두 미설정이다. 관측 상태를 이름만 바꿔 검증 승인하거나 임의값으로 예측하지 않았다.
- 기존 예측 원장은 한글·구분자가 있는 실제 KRX 이벤트 ID를 거절하고 종목코드를 저장하지 않는 결함이 있었다. 허용 형식을 수정하고 새 예측에는 6자리 거래코드와 시장을 저장한다. 과거에 신원 없는 예측이 있다면 소급 변경하지 않고 검토 대기로 남긴다.
- resolve_prospective_prices.py는 미평가 예측만 순회하며 상장일 21시 이후에만 공식 가격을 호출한다. 반환 코드·시장·거래일의 정확 일치를 요구하고 회사명 보조 매칭만으로 승인하지 않는다. 공식 응답 근거를 별도 파일로 보존하고 기존 평가를 다시 호출하지 않는다. 한 종목의 오류가 다음 종목 처리를 막지 않으며 예외 메시지/헤더/키는 실행 기록에 넣지 않는다.
- 실제 원장은 여전히 예측 0건이므로 사후 평가 배치는 API 호출 없이 빈 실행으로 완료됐다. 실제 KRX 키 호출 검증은 미실행이며, 정상/실패/재실행은 모의 응답 테스트로 확인했다.

```bash
python ipo_predictor/scripts/collect_upcoming_ipo.py \
  --submission-start 2026-06-01 --submission-end 2026-09-22

python ipo_predictor/scripts/resolve_prospective_prices.py \
  --database ipo_predictor/data/processed/prospective/listing_eve.sqlite \
  --output ipo_predictor/data/processed/prospective/price_runs
```

두 명령은 스케줄러에서 호출 가능한 단발 배치다. 아직 완성되지 않은 DART 승인 연결을 무시하고 자동 운영을 켜지 않았으며 OS/서버 스케줄러는 등록하지 않았다. 키가 있는 실행 환경에서 신규 후보의 공식 신원을 연결하고 표본 검증을 통과한 다음 스케줄을 활성화해야 한다. 아래 9/16 절은 당시 구현 상태의 이력이다.

## 현재 상태와 범위

2026-09-16 연구용 예측 기록 및 공식 가격 평가 CLI를 추가했다. 서비스 출시 보류는 유지한다. 기존 2026년 최종 평가를 반복하거나 모델 설정을 바꾸지 않는다. 기존 저장소의 예측 upsert는 과거 기록을 덮어쓰므로 연구용 SQLite 원장을 별도로 사용한다.

실제 로컬 features_all.parquet의 2026-09-16 이후 상장 예정 행은 0건이다. 따라서 실종목 예측은 발행하지 않았다. 합성 테스트는 기능 검증일 뿐 모델 성능 근거가 아니다.

## 구현된 처리

1. predict: 고정 실험 manifest와 개발 데이터 해시를 검사하고 기존 개발 데이터만으로 동일 모델을 학습한다. 2026년 holdout은 열지 않는다. 시초가 트리 모델과 평균·중앙값 기준선, 종가 평균·중앙값 기준선을 기록한다.
2. 입력: 일반 IPO 및 KOSPI/KOSDAQ만 허용한다. 피처 목록은 실험 계약과 정확히 일치해야 한다. 기관 경쟁률·통합 확약은 필수이며 확약 단위는 0~1이다. 개인청약은 계약에 없고 사용하지 않는다.
3. 시점: 실제 시스템 시각으로 상장 전날 21:00~23:59 KST에만 기록한다. CLI에 과거 시각 지정 옵션은 없다. 원천 공개시각 <= 수집시각 <= 입력 기준시각을 검사하며 모든 시각에 시간대가 필요하다.
4. 근거: 값과 감사 원시값 일치, 검증 상태, 사람 검토 불필요를 확인한다. 입력 출처는 DART/KRX/공식 주관사/공식 데이터 파생값에 한정한다. 임의 URL이나 인증 헤더 대신 공개 문서 식별자를 저장한다. 결측은 허용된 사유와 함께 NULL로 유지하고 학습 구간 중앙값으로만 전처리한다.
5. 원장: event_id별 한 번만 INSERT한다. 예측의 UPDATE/DELETE와 중복 입력은 차단한다. 입력·근거·시각·모델 설정·학습 해시·예측을 함께 보관하며 SHA-256으로 읽기 시 변조를 확인한다.
6. resolve: 상장 당일 21:00 KST 이후에 해당 이벤트·날짜의 검증된 KRX 정규장 시가/종가만 연결한다. 시간외 가격을 종가 타깃으로 사용하지 않는다. 확정 공모가 대비 수익률과 방법별 절대오차를 예측과 별도 테이블에 기록한다.

## 실행 인터페이스

저장소 루트에서 실행한다. 아래 입력 파일은 **신규 공식 수집기의 검증 산출물**이어야 한다. 사람이 검증 상태 문자열만 임의로 붙인 파일은 공식 검증 완료가 아니다.

```bash
python ipo_predictor/scripts/prospective_listing_eve.py status \
  --database ipo_predictor/data/processed/prospective/listing_eve.sqlite

python ipo_predictor/scripts/prospective_listing_eve.py predict \
  --database ipo_predictor/data/processed/prospective/listing_eve.sqlite \
  --experiment ipo_predictor/data/processed/experiments/listing_eve_v1/636eae2880f279a3 \
  --input <검증된_상장예정_입력.json>

python ipo_predictor/scripts/prospective_listing_eve.py resolve \
  --database ipo_predictor/data/processed/prospective/listing_eve.sqlite \
  --input <검증된_KRX_상장일_가격.json>
```

predict 입력은 event_id, listing_date(YYYY-MM-DD), offering_type=general_ipo, market, offering_price, offering_price_evidence, features, evidence를 포함한다. evidence는 피처별 raw_value, source, source_reference, available_at, collected_at, verification_status=verified, human_review_required=false를 포함한다. 가격 근거에도 동일 필드가 필요하다. 결측 피처 근거에는 missing_reason을 남긴다.

resolve 입력은 event_id, price_date, session=KRX_REGULAR, open_price, close_price, evidence를 포함한다. evidence에도 해당 event_id, price_date, open_price, close_price가 있어야 하며 출처는 KRX다. 원문 근거를 이 인터페이스에 연결하는 수집 어댑터는 아직 구현되지 않았다.

## 남은 실제 운영 연결

- 현재 파이프라인은 과거 상장 결과 기반이다. 상장 예정 이벤트의 공식 일정과 상장 전 피처를 수집하는 어댑터가 필요하다. 과거 features_all을 재실행하는 것으로 이 기능을 대체할 수 없다.
- 기존 관측 원장의 검증 상태를 단순히 verified로 이름만 바꿔서는 안 된다. 신규 어댑터는 원문·규칙·이벤트 연결·공개시각을 검증해 입력 계약으로 변환해야 한다. 현 CLI는 신뢰된 내부 입력용이며 외부 사용자 입력 API가 아니다.
- 21시 작업의 자동 스케줄 등록, 재시도·누락 경보, 상장 일정 변경/취소 처리, 공식 정정 가격의 추가 버전 처리, 원장 백업은 아직 연결하지 않았다. 실패 입력은 원장을 수정하지 않고 오류를 반환한다. 정정이 필요하다고 기존 기록을 삭제해서는 안 된다.
- SQLite 트리거는 애플리케이션 실수에 대한 보호이며 관리자 파일 조작까지 막는 WORM 저장소가 아니다. 해시도 외부 서명/타임스탬프를 대체하지 않는다.
- 테스트가 통과해도 실제 예측 성능이 입증된 것은 아니다. 이후 신규 표본에서 사전 정의한 평가 기간·표본 기준을 별도로 고정해야 하며, 중간 결과를 보고 반복 조정하지 않는다.

이번 완료 범위는 기록·평가 코드 경로와 테스트다. 자동 수집부터 일정 실행까지 모두 가동됐거나 앱 출시가 완료됐다고 주장하지 않는다.
